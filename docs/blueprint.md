# DoseCheck product and architecture notes

DoseCheck is a local-first medication log built around a narrow question:

> What have I already logged today, and what is still unresolved?

The app is intentionally small. It focuses on reliable daily records, traceable corrections, and local reminders without turning the product into a treatment or dosage system.

## Product boundary

DoseCheck records user-entered actions. It does not make treatment decisions.

- A notification is a reminder, not proof that medication was taken.
- DoseCheck does not calculate or recommend insulin doses.
- An uncertain entry stays uncertain; the app does not tell the user to repeat it.
- The second-entry interval comes from the configured routine. It is not medical advice generated by the app.
- Duplicate logging is blocked in the normal Today flow.
- Corrections are made from History and remain traceable as new events.

These constraints shape both the UI and the data model.

## Product surfaces

DoseCheck has three primary destinations:

1. **Today** — current-day state and logging actions.
2. **History** — previous records, recorded amounts, and corrections.
3. **Settings** — routine configuration, reminders, language, safety/privacy information, and local-data reset.

There is no dashboard, adherence score, account flow, social layer, or analytics surface in the current version.

## State management

The app uses a small `DoseCheckController` built on `ChangeNotifier` rather than a third-party state-management package.

Its responsibilities are deliberately limited:

- load the local repositories at startup;
- expose the active routine and preferences;
- derive day state from the event history;
- persist mutations before exposing them as successful;
- prevent overlapping user mutations.

The UI listens to the controller through Flutter's built-in `ListenableBuilder`.

## Event-based medication history

DoseCheck does not store a second mutable "current status" table.

A `DoseEvent` records:

- a stable id;
- the local calendar-day key;
- the dose slot;
- the event type (`taken`, `missed`, `uncertain`, or `cleared`);
- the real UTC event timestamp;
- the recorded amount when the event represents a taken dose.

`DoseDayState` derives the current state for each slot from that event stream.

### Why corrections append events

A correction adds a `cleared` event rather than deleting the original record. The latest effective event determines the current status, while the history can still show what happened before the correction.

This keeps corrections auditable without introducing a full event-sourcing framework.

### Historical amounts

Taken events snapshot their recorded amount. Changing the configured routine later therefore does not rewrite the meaning of historical entries.

## Routine model

`RegimenPlan` stores the configurable values required by the current product:

- morning tablet quantity and reminder time;
- second tablet quantity and minimum interval after the confirmed morning entry;
- night insulin default amount and reminder time.

The configured values describe the user's existing plan. DoseCheck does not derive or recommend them.

## Persistence

Hive CE stores local data in two boxes:

- `dosecheck_events_v1` — dose events;
- `dosecheck_settings_v1` — regimen and app preferences.

Domain objects serialize to primitive maps with explicit schema versions. This keeps the stored format readable and makes future migration decisions explicit.

All repository mutations are awaited before the controller publishes the corresponding in-memory change.

### Reset behavior

Resetting local data clears settings before dose history. The two Hive boxes do not provide one cross-box transaction, so the reset order deliberately protects the more important history data if the settings clear fails.

If a later clear fails, the controller reloads the persisted state instead of pretending the reset completed.

## Reminder model

Local notifications are supported on Android and iOS.

- Morning and night use recurring local-time reminders.
- The second reminder is one-shot and exists only after a confirmed morning `taken` event.
- Uncertain or missed morning entries never create the second reminder.
- Once a second reminder is due or the second entry is resolved, no future one-shot reminder is kept for that entry.
- Android uses inexact-while-idle scheduling; DoseCheck does not request exact-alarm privileges.
- The Android boot receiver is configured so the notification plugin can restore scheduled notifications after a restart.

Reminder scheduling decisions are separated from the platform plugin so the rules can be unit tested without a device.

The device service serializes mutations to the notification IDs and skips identical successful plans. A failed synchronization is never cached as successful, so a later state/dependency change can retry it.

Web and desktop builds keep the logging UI and local records but do not schedule medication notifications.

## Time model

Dose events store both:

- an absolute UTC timestamp; and
- the local calendar day to which the record belongs.

That avoids reinterpreting historical day membership solely from the device's current timezone.

The second-entry availability time is derived from the confirmed morning event plus the configured minimum interval.

## Localization

English, French, and Arabic ship from the same feature surfaces using Flutter's generated localization system.

Arabic uses the same widgets under right-to-left layout rather than a separate implementation. User-visible feature copy stays in ARB files instead of being embedded in presentation widgets.

## Visual system

The UI uses a small design layer for:

- light and dark color schemes;
- typography and Material component defaults;
- runtime asset paths;
- the DoseCheck brand mark;
- shared content-width behavior.

The design stays intentionally quiet: strong spacing and type hierarchy, restrained surfaces, and status colors reserved for meaningful state.

## Failure behavior

DoseCheck treats persistence as authoritative.

- A log entry does not appear as saved until its repository write succeeds.
- Failed preference or routine writes leave the active controller state unchanged.
- Bootstrap failures show a recoverable local-data error instead of opening an empty app that could be mistaken for valid history.
- Reminder failures do not alter medication records.

## Test strategy

The repository contains focused tests for:

- day-state derivation and second-entry timing;
- event and settings serialization;
- controller mutation and persistence-failure behavior;
- reminder schedule decisions;
- English/French/Arabic layout direction;
- packaged runtime assets;
- a widget-level application smoke path.

CI runs formatting checks, static analysis, tests, and an Android build before changes reach the main branch.

## Current non-goals

The current version intentionally does not include:

- accounts or authentication;
- backend or cloud synchronization;
- glucose tracking;
- dosage recommendations or AI;
- adherence scoring or charts;
- doctor/family sharing;
- refill inventory;
- watch integration.

Those are separate product decisions, not missing placeholders in the current UI.
